# sql/

SQL-миграции целевой Supabase-схемы (§38 `PLATFORM_TARGET_ARCHITECTURE.md`).
Выполняются **вручную** — приложение и anon-ключ не могут выполнять DDL.

## Как выполнить `002_create_platform_v2_tables.sql`

1. Открыть Supabase Dashboard связанного проекта (`https://api.rbi-q.ru`).
2. Перейти в **SQL Editor**.
3. Вставить содержимое файла целиком, нажать **Run**.
4. Убедиться, что выполнение прошло без ошибок (создаются 13 новых таблиц
   + RLS-политики).

## Если ошибка «таблица уже существует»

Не будет — все `CREATE TABLE IF NOT EXISTS`, повторный запуск безопасен.
Если ошибка на этапе `DO $$ ... $$` (политики) — вероятно, политика с тем
же именем уже создана вручную; скрипт сам делает `DROP POLICY IF EXISTS`
перед созданием, повторный запуск также безопасен.

## Откат

Раскомментировать блок `ROLLBACK` в конце `002_...sql` и выполнить —
удаляет все 13 новых таблиц. Старые таблицы не затрагиваются никогда.

## Как выполнить `003_extend_contractors_and_contracts.sql`

1. Открыть Supabase Dashboard связанного проекта (`https://api.rbi-q.ru`).
2. Перейти в **SQL Editor**.
3. Вставить содержимое файла целиком, нажать **Run**.
4. Убедиться, что выполнение прошло без ошибок (6 новых колонок у
   `contractors` + новая таблица `contracts` с RLS-политиками).

Повторный запуск безопасен — `ADD COLUMN IF NOT EXISTS`/
`CREATE TABLE IF NOT EXISTS`, политики пересоздаются через
`DROP POLICY IF EXISTS`.

Откат — раскомментировать блок `ROLLBACK` в конце `003_...sql`. Старые
таблицы и существующие 7 полей `contractors` не затрагиваются никогда.

### 015_plan_fact_cloud.sql — модуль plan-fact (План/Факт СМР)

Таблицы `plan_fact_imports`, `plan_fact_wor`, `plan_fact_facts`, `plan_fact_norms`, `plan_fact_calendar`:
ВОР, факт прораба (сторно через `corrects_id`/`superseded_by`), нормы ПТО и рабочий календарь компании.
Доступ: только `authenticated`, строки ограничены проектом (`rbi_current_project_code()`) и подтверждённым
доступом (`rbi_is_approved()`); `anon` не получает ничего. Объёмы — `numeric`, не float (правило «числа только decimal»).
**Применить вручную до включения отправки ВОР и факта в облако** (DDL недоступен anon-ключу).

### 017_plan_fact_contours_and_approval.sql — ТЗ-2: контуры объёмов и утверждение

Шесть таблиц: `plan_fact_wor_quantities` (контуры RD/CONTRACT/PROPOSED/APPROVED/FACT/CUSTOMER_ACCEPTED,
уникальность «позиция + контур»), `plan_fact_proposals` и `plan_fact_proposal_rows` (пакет ПТО),
`plan_fact_baselines` (неизменяемый снимок, UPDATE/DELETE запрещены триггером),
`plan_fact_change_requests` (корректировка: было/стало, причина, решения) и `plan_fact_audit`
(append-only аудит: кто, когда, почему, до/после). Доступ — только `authenticated`, по проекту;
`anon` не получает ничего. **Применить до включения контуров и утверждения в модуле.**

### 018_plan_fact_hardening.sql — hardening plan-fact

Три вещи: (1) триггер неизменяемости теперь срабатывает только для ролей приложения
(`authenticated`, `anon`) — владелец схемы может исправить ошибку, приложение по-прежнему
не может переписать аудит или baseline (защита остаётся на политиках RLS); (2) `updated_at`
ставит база триггером — правки вне приложения больше не пропускаются инкрементальным приёмом;
(3) индексы `(project_code, updated_at, id)` под постраничный приём.
**FORCE ROW LEVEL SECURITY сознательно не включаем** — владелец должен сохранять возможность
починить ошибку; отклонение зафиксировано в ADR-016.
Заодно в комментарии миграции — SQL для уборки двух тестовых строк (`__SMOKE_TEST__`).

### 019_plan_fact_works_catalog.sql — ТЗ-4: справочник работ как данные

Две таблицы: `plan_fact_works` (вид работ: код, название, единица, этап, группа, правило расчёта,
версия, источник `builtin`/`pto`) и `plan_fact_work_aliases` (связки «название в форме → вид работ»,
уникальность по нормализованному названию). Справочник **корпоративный** (`company_id = 'rbi'`),
доступ только `authenticated`, `anon` не получает ничего; время записи ставит триггер из `sql/018`.
**Применить до того, как ПТО начнёт править справочник в интерфейсе.**
